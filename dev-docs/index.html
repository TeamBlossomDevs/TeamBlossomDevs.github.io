Team Blossom Documentation

This page defines the core identifiers, file formats, directory layout patterns, and naming conventions used by the Team Blossom toolchain.

The goal: short names, low collision risk, and stable meaning across the entire engine + tooling ecosystem.

Core Components

blm — GML Translation Layer

Purpose: A C-based mapping + runtime bridge between GML and native systems.
Responsibilities: symbol mapping, ABI compatibility, code emission, runtime bridging.

Blossom Language Mapping

petal — Unified Programming Language

Purpose: Replaces the traditional “C + ASM + GML” combination with a single cohesive language.
Scope: low-level control, high-level scripting, tooling integration, engine glue.

.bdef — Shared Headers / Definitions

Purpose: ABI-stable declarations and shared interfaces. Used anywhere you would traditionally rely on shared header files. 

core.bdef
math.bdef
render.bdef
abi.bdef

All File Formats

These extensions are reserved for Team Blossom usage. Each extension has exactly one meaning. This list includes every format we defined together.

Extension / Name Category What it stores Typical location

petal Language Unified language replacing C+ASM+GML /petal/
.bdef Definitions Shared declarations, constants, ABI-stable interfaces /bdef/, /defs/
.blsm 3D Models Meshes, rigs, animations, engine metadata /assets/models/

Why custom file formats exist

Team Blossom is open source by design, which means the engine and tools are intentionally transparent. However, game content (assets, maps, dialogue, cutscenes, music, saves) still represents creative work that can be easily ripped and re-uploaded if it’s stored as plain, universally-readable files.

Because of that, Team Blossom uses custom formats primarily as a practical anti-piracy / anti-repackaging measure: not to be “unbreakable DRM”, but to add enough friction that someone can copy a folder of assets to the desired source with a legally aquired copy.

  • Prevents “drag-and-drop repacks”: assets aren’t immediately usable outside the pipeline/Legal copy..
  • Toolchain control: conversion/import happens through official tools, where rules can apply.
  • Versioned decoding: formats can enforce compatibility and validation checks.
  • Modding with boundaries: mods can be supported through converters without exposing raw masters.

This keeps the project open source while still protecting original game content from effortless redistribution.

Naming Conventions

General Rules

  • Lowercase only for core identifiers and extensions.
  • No hyphens in canonical names (use underscores in source files).
  • Short and stable beats descriptive and trendy.
  • One meaning per extension — never overload a format name.
  • Prefer subsystem prefixes for code files to reduce collisions.

Map Structure Files

Team Blossom uses .bmap for map structure files. These files describe map layout, object placement, triggers, collisions, and navigation data. The runtime loads .bmap and connects it to dialogue, scripted events, and assets like models/textures.

Random example file name: weaveyard_07a.bmap

.bmap — What it stores

  • Map ID and version
  • Tile layers or chunk layers
  • Collision shapes / navigation data
  • Object instances (NPCs, props, triggers)
  • Links to scenes/dialogue (.bdlg) and music (.bsng)
  • Optional streaming rules (load zones)

Structure concept

Internally, .bmap is intended to be chunk-based:

  • Header: magic + version + flags
  • Chunk directory: offsets/lengths so data can be skipped/streamed
  • Chunks: each chunk is a typed block (tiles, objects, nav, triggers, etc.)

Example (human-readable shape)

# weaveyard_07a.bmap (example shape)
format: bmap
version: 1
map_id: weaveyard_07a
size:
  width: 160
  height: 120
layers:
  - name: ground
    type: tile
    source: weaveyard_ground.tileset
  - name: deco
    type: tile
    source: weaveyard_deco.tileset

collision:
  type: grid
  source: weaveyard_collision.bin

objects:
  - id: npc_guard_01
    kind: npc
    x: 34
    y: 62
    dialogue: npc_guard.bdlg
  - id: trigger_gate
    kind: trigger
    x: 110
    y: 40
    w: 4
    h: 2
    on_enter: gate_open

audio:
  music: ambient_forest.bsng

Save File Structure

Team Blossom uses .bsav for save data. Save files are designed to be compact, versioned, and safe to evolve over time without breaking older saves.

Random example file name: slot2_millfield_2f9c.bsav

.bsav — What it stores

  • Player location (x, y, and map reference)
  • Inventory items (+ quantities, optional metadata)
  • Party members (who is in the party, order, optional stats)
  • Route selection (numeric route: 1, 2, 3)
  • Flags / story progression bits
  • Optional timestamp + playtime counters

Structure concept

Internally, .bsav is intended to be chunk-based and versioned, similar to:

  • Header: magic + version + checksum
  • Sections: player, world, inventory, party, route, flags
  • Forward compatibility: unknown sections are safely skipped

Example (human-readable shape)

{
  "schema": "bsav",
  "version": 1,

  "slot": 2,
  "game_id": "millfield",
  "timestamp": 1734801212,
  "playtime_seconds": 5420,

  "world": {
    "map": "weaveyard_07a.bmap",
    "x": 110,
    "y": 41,
    "route": 2
  },

  "party": [
    { "id": "alex", "hp": 18, "max_hp": 22 },
    { "id": "ivy", "hp": 12, "max_hp": 18 }
  ],

  "inventory": [
    { "id": "potion_small", "qty": 3 },
    { "id": "key_rusty", "qty": 1, "meta": { "opens": "gate_a" } }
  ],

  "flags": {
    "met_guard": true,
    "gate_opened": false,
    "took_side_path": true
  }
}

Route system

Route is represented as an integer to keep the save format compact and stable: 

route = 1  -> Route 1
route = 2  -> Route 2
route = 3  -> Route 3

Route should not be inferred from dialogue or combat outcomes at load time. Save files store the chosen route explicitly, while flags track what caused it.
