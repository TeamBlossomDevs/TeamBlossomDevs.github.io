Team Blossom Documentation

This page defines the core identifiers, file formats, directory layout patterns, and naming conventions used by the Team Blossom toolchain.

The goal: short names, low collision risk, and stable meaning across the entire engine + tooling ecosystem.

Core Components

blm — GML Translation Layer

Purpose: A C-based mapping + runtime bridge between GML and native systems.
Responsibilities: symbol mapping, ABI compatibility, code emission, runtime bridging.

Blossom Language Mapping

petal — Unified Programming Language

Purpose: Replaces the traditional “C + ASM + GML” combination with a single cohesive language.
Scope: low-level control, high-level scripting, tooling integration, engine glue.

.bdef — Shared Headers / Definitions

Purpose: ABI-stable declarations and shared interfaces. Used anywhere you would traditionally rely on shared header files. 

core.bdef
math.bdef
render.bdef
abi.bdef

All File Formats

These extensions are reserved for Team Blossom usage. Each extension has exactly one meaning. This list includes every format we defined together.

Extension / Name Category What it stores Typical location
blm Tool / runtime GML translation layer (C ↔ GML bridge) /blm/
petal Language Unified language replacing C+ASM+GML /petal/
.bdef Definitions Shared declarations, constants, ABI-stable interfaces /bdef/, /defs/
.blsm 3D Models Meshes, rigs, animations, engine metadata /assets/models/
.btex Textures Texture container (mipmaps, compression, metadata) /assets/textures/
.bdlg Dialogue Plaintext-like dialogue + branching choices + conditions /assets/dialogue/
.bsng Music Song/adaptive music data (loops, layers, markers) /assets/music/
.bvid Video Cutscenes + playback metadata + transitions /assets/video/
.bnet Network / Stats Networked choice state + global percentages + sync /network/

Naming Conventions

General Rules

  • Lowercase only for core identifiers and extensions.
  • No hyphens in canonical names (use underscores in source files).
  • Short and stable beats descriptive and trendy.
  • One meaning per extension — never overload a format name.
  • Prefer subsystem prefixes for code files to reduce collisions.

Subsystem Naming

Subsystems own their prefix and define a small internal namespace: blm_*, petal_*, and so on. 

blm_runtime.c
blm_emit.c
blm_abi.c

petal_parse.c
petal_codegen.c
petal_vm.c

File Format Naming

  • Extensions begin with b for Blossom-owned formats: .btex, .bvid, .bnet, etc.
  • Formats are grouped under /formats/<ext>/ with a spec.md and examples/.
  • Versioning should be embedded in the file header (magic + version), not by changing the extension.

Public vs Internal Variants

Canonical formats keep their stable extension. Experimental versions may add suffixes to filenames or directory names, but the extension should remain stable unless the format is truly different. 

btex_raw/        (dev tooling output)
bnet_debug/      (internal test fixtures)
petal_ir/        (internal compiler phase)

Format Samples

These samples are intentionally small and human-readable. They show the “shape” of each format. You can lock these into formal specs later (chunked binary, strict parsers, etc.).

.bdlg (Dialogue) — plaintext-like example

# intro.bdlg
@scene intro

[Speaker:Narrator]
Welcome to Millfield.

[Speaker:Alex]
So this is the place?

[Choice]
- "Yeah. Let's go." -> goto start_adventure
- "Nope. I'm leaving." -> set flag=left_early; goto ending_leave

@if flag=left_early
[Speaker:Narrator]
You walked away before it even began.

.bnet (Network / Choice State) — JSON-shaped example

{
  "schema": "bnet",
  "version": 1,
  "game_id": "millfield",
  "session_id": "local:9b2f1d",
  "choices": {
    "intro_accept": { "picked": "yes", "timestamp": 1734800000 },
    "save_farmer": { "picked": "no", "timestamp": 1734800500 }
  },
  "global_percentages": {
    "intro_accept": { "yes": 78.4, "no": 21.6 },
    "save_farmer": { "yes": 41.2, "no": 58.8 }
  }
}

.bdef (Definitions) — header-like example

// core.bdef (example shape)

  unsigned int id;
